    La aplicación prepara la petición

    Antes de mandarte a iniciar sesión, la aplicación genera tres valores aleatorios y los guarda: state (contra CSRF), nonce (contra reutilizar un id_token) y el code_verifier de PKCE. Al servidor solo le envía el hash del verifier: el code_challenge.

    Canjear el código por tokens
    
      
    La aplicación envía el código junto con el code_verifier original. El servidor calcula su SHA-256 y lo compara con el code_challenge del paso 1. Así, aunque alguien robara el código, no podría canjearlo.

      Usar el access_token
      
      
      El access_token es la llave para llamar a APIs. El id_token solo sirve para que la aplicación sepa quién eres: no debe usarse para llamar a una API, y este servidor lo rechaza.

    Lo que este laboratorio simplifica
    
    
      
      
    • Hay un único usuario de prueba y no se pide contraseña: el foco está en el protocolo, no en la autenticación.
      • 
      
    • El código de autorización es un JWT firmado y sin estado, válido 60 segundos. Un servidor real lo guarda y lo invalida al primer uso, para impedir que se canjee dos veces.
      • 
      
    • Los tokens se guardan en sessionStorage para poder mostrarlos. En una aplicación real se evita exponerlos así (por ejemplo, con un backend-for-frontend).
      • 
    
    
    
    Configuración pública del servidor: /.well-known/openid-configuration · /as/jwks
